## 1. График отпусков

Страницы: `/vacations` (сотрудник и руководитель), `/admin/vacations` (админ/HR).

### 1.1. Что можно сделать

| Роль | Возможности |
|------|-------------|
| Сотрудник | Выбрать даты → подать заявку; поставить **предварительную бронь** (месяц + длительность без точных дат); смотреть свой календарь и **общий** календарь команды (где доступно); править/удалять свои `pending` и согласованные, пока отпуск не полностью прошёл; пройти обучалку |
| Руководитель группы / отдела | Согласовать или отклонить заявки своей зоны; смотреть статистику команды; режим «как сотрудник» |
| Директор отдела (Digital и т.п.) | Второй шаг согласования для подчинённых групхедов; дневные счётчики отпускников по отделу |
| Admin / HR | Добавить отпуск сотруднику из графика; rollover учётного года; полный обзор |

### 1.2. Статусы заявки

| Статус | Смысл |
|--------|--------|
| `pending` | На согласовании (есть ещё `approval_step`) |
| `approved` | Согласована |
| `rejected` | Отклонена |

**Отклонённые заявки не влияют на остаток дней.**

### 1.3. Этапы согласования

Обычный отдел (один согласующий — руководитель из справочника):

```
подача → pending (manager) → approved | rejected
```

**Двухэтапные** отделы (сейчас: **Digital**, демо QA на localhost): сотрудник под **групхедом** (в Digital: Попов / Лунин / Цхай / Носков):

```
подача → pending (manager = групхед)
         → pending (director = директор отдела)
         → approved | rejected
```

- Самосогласование **запрещено**: согласующий не может утвердить свою же заявку.
- Заявка **директора отдела** в двухэтапном отделе идёт к его руководителю (`manager`), не к самому себе на шаге director.
- У **генерального директора** (`manager` пустое — так и должно быть: он никому не подчинён) заявку согласуют **admin/HR** из админки; отдельного «руководителя над гендиром» в справочнике нет.
- После финального `approved` — синк отсутствия в Bitrix (пальма), если настроен вебхук/OAuth (см. `BITRIX.md`).
- Смена дат у согласованной заявки — обновляет отсутствие в Bitrix; отклонение или удаление — снимает пальму.
- Если синк с Bitrix не удался (создать / обновить / снять) — уведомление админу в колокольчике платформы.

Уведомления: в платформе (колокольчик сотрудника/руководителя) и параллельно в Bitrix **`im.notify.system.add`** (без личных чатов для согласования).

### 1.3.1. Напоминания от чат-бота Bitrix (не согласование)

Канал: бот **VBI HR** (`imbot.message.add`, `BITRIX_IMBOT_ID=2830`). Подробности и установка timers: **[BITRIX.md](./BITRIX.md)**.

| Кому | Когда (МСК) | Что |
|------|-------------|-----|
| Сотрудник | проверка **каждый день в 12:00**; письмо **один раз** | `approved`, старт **ровно через 21 день** → заявление + передача проектов; для Digital / SEO·ORM — ссылка на памятку отдела |
| Руководитель | **1-е в 11:15** | `approved` со стартом **в текущем месяце** (учесть отсутствие) |
| Руководитель | **15-е в 11:15** | `approved` со стартом **в следующем месяце** (спланировать передачу дел) |

**Зоны руководителя:** Ревзина — весь Digital; Музыка / Трубицына / Волдайский / Малиновская / Лашин — весь свой отдел (у Лашина — Отдел продаж); групхеды и прочие — только прямые подчинённые. **Юдин Вадим не получает** эти сообщения.

Тексты сотрудника (без памятки):

```
До отпуска осталось 3 недели (ДД.ММ.ГГГГ — ДД.ММ.ГГГГ).

Пожалуйста, заранее:
1. Напишите заявление на отпуск.
2. Поставьте задачи на передачу проектов на время отпуска.
```

Памятки: Digital → https://crm.vbi.ru/devs/21301/ ; SEO / ORM → https://crm.vbi.ru/devs/24611/ .

### 1.4. Как считаются дни отпуска (длина периода)

Формула: **календарные дни от `start` до `end` включительно, минус официальные праздники РФ** из производственного календаря платформы.

| Учитывается | Не учитывается |
|-------------|----------------|
| Будни | Праздники из списка года (`isRuHoliday`) |
| **Выходные (сб/вс)** — входят в счёт | |

Код: `countVacationBillableDays` / `countVacationBillableDaysInYear` в `vacationCalendar.ts`.  
Календари **2026** и **2027** зашиты в том же файле (праздники + переносы длинных каникул); для других лет без списка праздники = 0 исключений.

Заявка через Новый год лежит в папке года **даты начала**, но в баланс каждого учётного года входят только billable-дни, попадающие в этот календарный год (хвост января списывается из баланса следующего года, а не «теряется»).

Пример: 1–7 янв при новогодних каникулах в списке — в счёт попадут только дни **вне** праздничного набора.

### 1.5. Остаток дней отпуска (баланс)

Отображение в боковой панели: **остаток / отгулял / план**.

**Начисление «положено» к дате:**

1. База на 1 января учётного года (`primaryYear`):
   - если в карточке сотрудника задан `vacation_opening_balance` — берём его;
   - иначе — оценка по модели ЗУП от даты найма (`hired_at`) к 01.01.
2. Плюс начисление с 01.01 по «сегодня» (та же ЗУП-модель, норма **28 дней/год**, события начисления ≈ раз в месяц от даты найма, результат с точностью до 0,1).

**Вычитается из остатка:**

| Учитывается в остатке | Не учитывается |
|-----------------------|----------------|
| Дни заявок со статусом **`approved`** (billable) | `rejected` |
| Дни заявок со статусом **`pending`** (billable) | Предварительные **брони** |
| | Идеи, задачи, магазин и прочее |

Остаток = `max(0, положено − approved − pending)`, округление вниз до 0,1.

**Колонки «Отгулял» / «План»** (только `approved` + `pending`):

- **Отгулял** — согласованные дни, уже прошедшие (для текущего отпуска: часть до сегодня включительно).
- **План** — все `pending` целиком + будущая часть согласованных (и хвост текущего отпуска после сегодня).

### 1.6. Проверка «хватит ли дней» при выборе дат (аванс)

Перед подачей считается доступный остаток **на дату начала** выбранного периода (`calcAvailableOnDate`):

- начисление к дате начала;
- минус `approved` и `pending` **по дату начала** (не весь будущий хвост после неё в этой проекции).

Если нужных billable-дней больше, чем доступно → статус **аванс** (можно подать, но UI предупреждает).  
Проекция «к прошлой дате» для будущего баланса не должна завышать текущий остаток: для UI «расчёт к дате» имеет смысл на **будущие** даты.

### 1.7. Учётный год

| Понятие | Смысл |
|---------|--------|
| `primaryYear` | Учётный год ЗУП: база остатка на 01.01 этого года |
| Год в UI / `requestsByYear` | Папка календаря; заявка кладётся в год **даты начала** |
| Архивные годы | У сотрудника — просмотр; правки в прошлом году ограничены |

Переход года: остаток на 31.12 → новый `vacation_opening_balance`, `primaryYear` += 1 (`vacationYearRollover`).

### 1.8. Предварительная бронь

- Месяц + длительность (1–28 дн.), **без** точных `start`/`end`.
- **Не** влияет на остаток и согласование.
- В календаре — полосатая плашка; «Уточнить даты» → обычная заявка.
- Нельзя создать бронь в прошедшем месяце и в **последний день** месяца брони.
- **Лимиты (Digital / демо QA):** до **5** броней на месяц на весь отдел; не более **1** брони на месяц внутри подгруппы. При исчерпании `+бронь` недоступна.

### 1.9. Доп. правила Digital

- **Групхеды:** не более одного групхеда в отпуске на пересекающиеся даты (`pending`/`approved`); иначе предупреждение в форме и отказ сервера (409).
- Пересечения отпусков коллег в UI подсвечиваются (информативно), отдельный жёсткий запрет — только правило групхедов выше.

### 1.10. Обучалки

- Сотрудник: квест по календарю/заявке (`useVacationTraining`).
- Руководитель: свой квест (`useManagerVacationTraining`).
- Ачивка «Календарь отпусков» у руководителя — после **обоих** квестов.

## 2. Банк идей

Страницы: `/ideas` (сотрудник), `/admin/ideas` (admin/HR). Плитка на профиле ведёт в банк идей.

Очередь общая на сервере (`ideas.json`): идеи и голоса видят все сотрудники, браузеры друг друга не перезаписывают. Стартовый список пустой (без демо).

### 2.1. Возможности сотрудника

- Предложить идею (категория, город, описание, вложение / drag-and-drop). Категории: Офисная среда, Процессы, Культура, IT и инструменты, Корпоративы и развлечения, Другое. Старое имя «Благополучие» при чтении очереди переименовывается.
- Голосовать 👍/👎.
- Фильтры (все/мои, категория, статус), поиск, сортировка (новые / старые / популярные / непопулярные).
- Цветные плашки сводки переключают фильтр статуса в тулбаре (без отдельной подсветки плашки).
- Удалить **свою** идею.
- Видеть комментарий админа к этапу (в т.ч. причину отклонения).

### 2.2. Этапы идеи

```
отправка
  → На рассмотрении (review)
       ├─→ Реализация (implementation)
       │      └─→ Реализовано (done)
       └─→ Отклонено (rejected)   ← обязателен комментарий с причиной
```

| Переход | Кто | Подтверждение | Комментарий |
|---------|-----|---------------|-------------|
| Создание → review | Сотрудник | — | — |
| Смена этапа | Admin / HR | Модалка подтверждения | Необязателен; при **отклонении — обязателен** (≥3 символа) |
| → Реализовано | Admin / HR | Модалка | Необязателен |

После создания: уведомление admin/HR (`idea_submitted`) → колокольчик, ссылка на `/admin/ideas`.

**При каждой смене этапа** автору идеи:
- уведомление в платформе (`idea_status_changed`, колокольчик сотрудника → `/ideas`);
- системное уведомление в Bitrix (`im.notify.system.add`, ссылка на `/ideas`); в текст попадает этап и комментарий (если был).

Админ может удалить любую идею.

### 2.3. Статистика и топ-авторов

- Счётчики у сотрудника (всего / по статусам) — по его идеям.
- **Топ-авторы:** только идеи со статусом **Реализовано** (`done`).
- Подпись в топе: «N реализованных идей» (N пересчитывается при каждом `done`; позиции в рейтинге меняются при необходимости).
- Голоса и идеи на рассмотрении / в реализации / отклонённые **не** увеличивают место в топе.

## 3. Уведомления сотрудника (колокольчик)

- Колокольчик показывает отпуска, идеи и др. (без заголовка «Отпуска»).
- Крестик в дропдауне: убирает карточку **только из колокольчика**; запись остаётся на `/notifications`.
- На странице `/notifications` хранится история; максимум **100** на пользователя — при новом 101-м удаляется самое старое.
- Полное удаление — крестик на странице `/notifications`.

## 4. Юбилеи стажа (в работе)

- Вехи: 1 / 5 / 10 / 15 лет от `hired_at`.
- Подарки / купон в магазине — на 5 / 10 / 15.
- Цепочка: напоминания → оверлей-поздравление → ачивка → купон → заказ набора → уведомление HR.
- Детали модели: `tenureAnniversary.ts`; бэклог — `.cursor/rules/achievements-backlog.mdc`.

### Публичная визитка

Клик по ФИО в «Твоя команда» (профиль) и по автору в банке идей → компактная карточка (не `/profile`): должность, отдел, стаж, ДР (`birthday`), публичные ачивки, идеи. Из графика отпусков **не** открывается. Эталон: `docs/design-refs/employee-visiting-card/`.

## 5. Адаптация — сценарии по ролям

Базовый трек: `vbi-standard-90`. Admin/HR на `/admin/adaptation` может **создавать, редактировать и удалять** сценарии (треки), затем назначать один сценарий сотруднику.

Стартовый каталог (можно менять в UI):

| id | Название |
|----|----------|
| `general` | Общий сценарий |
| `context-ads` | Специалист по контекстной рекламе |
| `target-ads` | Специалист по таргетированной рекламе |
| `sales` | Менеджер по продажам |

Сценарий хранит название, аудиторию и **доп. шаги** по фазам (`pre_start` … `probation_90`). При назначении шаги **добавляются** к базовому треку. Повторное назначение заменяет предыдущее. Удаление сценария снимает связанные назначения (последний сценарий удалить нельзя). Сотрудник видит название на `/adaptation`.

## 6. VPN и прокси (помощник)

Раздел `/vpn` — онбординг сотрудника (скачать клиент; выдача ключа через wg-easy). На бое открыт в пилоте отпусков (whitelist).

### Лимиты конфигов на человека

| Тип | Максимум | Куда |
|-----|----------|------|
| WireGuard | **1** | Mac |
| AmneziaWG | **2** | iPhone / Windows / Android |

Один ключ можно поставить на **несколько устройств** (телефон и ноутбук/ПК) — просто не включать VPN на двух сразу.

### Клиенты (шаг «Какое именно устройство?»)

| Устройство | Клиент | Откуда |
|------------|--------|--------|
| Mac | WireGuard | App Store |
| iPhone | AmneziaWG | [App Store](https://apps.apple.com/us/app/amneziawg/id6478942365?l=ru) |
| Windows | AmneziaVPN | [GitHub releases](https://github.com/amnezia-vpn/amnezia-client/releases) → `AmneziaVPN_*_x64.exe` |
| Android | AmneziaVPN | те же releases → обычно `AmneziaVPN_*_android9+_arm64-v8a.apk` |

Прокси (Telegram) — отдельный клиент Windows (`TgWsProxy_windows_7_64bit.exe`), без лимитов пиров WG/AWG. В помощнике напоминаем включить автовключение вместе с запуском компьютера.

Выдача ключа: `POST /api/vpn/keys` `{ kind: "wireguard" | "amnezia" }` (нужна сессия). Создаёт пир в wg-easy только если лимит не исчерпан; иначе возвращает уже выданные конфиги+QR. Удаление пиров из платформы не делается.

Имена в админке: WireGuard — `Фамилия_Amst_Wire`; AmneziaWG — `Фамилия_Amst_Aeza`, второй — `Фамилия2_Amst_Aeza`.
Фамилия: Bitrix «Фамилия Имя» → первое слово; демо «Имя Фамилия» (…Тестов/а) → последнее.

Админские панели и запрет удалять чужие пиры — rule `.cursor/rules/vpn-key-limits.mdc`, константы `frontend/app/data/vpnLimits.ts`. Env: `WG_EASY_*`, `AWG_EASY_*` (см. `.env.example`).

## 7. Профиль — ачивки и недавняя активность

На своём `/profile`:

1. **Ачивки** — до 2 рядов иконок без подписей; полный каталог в оверлее «Все».
   - **Превью блока «Ачивки»** — только **полученные**; «Календарь отпусков» первым (круглый PNG). Неполученные — только в оверлее «Все · N». Под ФИО — до 5 (без квеста).
   - **Выдача автоматически:** стаж 1 год по `hired_at`; 5/10/15 после claim юбилея (+ купон); ≥28 согласованных дней отпуска за учётный год; реализованные идеи; покупки в магазине (каталог + юбилейный заказ, **не** ручная лента).
   - **Выдача вручную** (`/admin/activity`): `talk`, `learning`, `promotion`, `mentor`, `practice`.
   - **Лучший специалист продаж** (`sales-best-1`…`5`): админ выбирает на `/admin/sales-best` (напоминание в колокольчик **29-го** МСК). Лучший — кто выше всех перевыполнил план. Ачивка в профиле только с **первого рабочего дня** следующего месяца (`reveal_on`, код + производственный календарь РФ) — до этого победитель скрыт. Перевыбор до reveal разрешён. В день reveal — запись в **Недавнюю активность** и **Новости коллег**.
   - **Оверлей «Все»** — 6 секций: Стаж и карьера · Отпуск · Выступления и кейсы · Обучение · Магазин · Лидерство и инициатива (идеи, наставник, практика, лучший ОП).
   - **Отпуск:** пока отдельный блок (1 ачивка); позже возможно объединение с «благополучием».
   - Журнал (`journal-*`) — пока без источника.
2. **Недавняя активность** — лента событий; **новые сверху** (сортировка по `occurred_at`).
3. **Команда** — коллеги (без себя).

Раскладка:

| Коллег в блоке команды | Слева | Справа |
|------------------------|-------|--------|
| ≤ 5 | ачивки → команда | активность |
| ≥ 6 | ачивки → активность | команда |

Источники активности:

| Источник | Примеры |
|----------|---------|
| Авто | юбилей → «Достижение»; обучение отпускам; купон/заказ → «Магазин»; идея в работе/done |
| Ручные (admin/HR) | выступление, признание, велком, другое — `/admin/activity` |
| Сид (тест) | записи у «Юбилеев Тест» (`jubilee@vbi.local`) |

Типы (8 значков в `public/activity/icons/`): магазин, выступление, обучение, идея, достижение, признание, велком, другое. Отпуск в ленту не кладём.

## 8. Оргструктура (просмотр и панель сотрудников)

Страницы: `/organization` (сотрудник, только просмотр), `/admin/organization` (admin/HR — редактор; превью «глаз» как у сотрудника).

### 8.1. Что видит сотрудник

| Действие | Результат |
|----------|-----------|
| Открыл `/organization` | Схема **целиком в кадре**, без внутреннего скролла (contain). Белое поле с равным зазором от шапки и низа экрана. |

## 9. Удаление сотрудника из справочника Vibe

### 9.1. Кто может войти

Вход в платформу — **только** для людей из справочника «Сотрудники» (`employees.json`).

- OAuth Bitrix успешен ≠ доступ в Vibe: если пользователя нет в справочнике (экстранет, практиканты, гости портала) — **403**, сессия не создаётся.
- Уже выданная Bitrix-сессия на каждом API-запросе перепроверяется: нет в справочнике → cookie сбрасывается.
- Удалённые из справочника — denylist + тот же отказ (см. ниже).
- Синк при входе / кнопка «синхронизировать из Bitrix» **обновляет** уже заведённых, **не импортирует** новых ACTIVE с портала.
- Демо-логин/пароль на **production** отключён (API и UI).

### 9.1.1. Сессия и безопасность входа

| Мера | Как сейчас |
|------|------------|
| TTL cookie | **8 часов**, скользящее продление при активности (если осталось < 4 ч) |
| Secure | `Secure`, если `APP_PUBLIC_URL` / redirect на **https** (или `VBI_COOKIE_SECURE=true`); на текущем HTTP-бою флаг не ставится, иначе cookie не прилипнет |
| Подпись | HMAC-SHA256 (`VBI_SESSION_SECRET` или производная от `BITRIX_CLIENT_SECRET`); сырой JSON без подписи не принимается |
| Справочник | Bitrix OAuth без записи в employees → 403; сессия на каждом API перепроверяет roster/denylist |
| XSS | CSP (default-src self + Метрика/шрифты), без `v-html` на пользовательских строках, HTML в идеях срезается при сохранении |
| Секреты | `BITRIX_CLIENT_SECRET` / webhook только server runtimeConfig (не `public`); webhook в логах редактируется; oauth-debug только localhost |

### 9.2. Что происходит при удалении

Удаление из «Сотрудники» **сразу закрывает доступ**: запись в denylist (`employee-access-denylist.json`), сессия сбрасывается при следующем API-запросе, повторный вход через Bitrix/демо отклоняется. Синк Bitrix **не возвращает** удалённого в справочник, пока его снова не добавят вручную.

| Данные | После удаления |
|--------|----------------|
| Справочник / общий календарь команды / панель оргсхемы | Нет в списках |
| Доступ (сессия, логин) | Закрыт сразу |
| VPN-ключи | Удаляются в учёте платформы **и** в панели wg-easy; если удалить пир не удалось — уведомление админу `vpn_peer_delete_failed` |
| Уведомления сотрудника | Очищаются сразу |
| Аватар | Живёт **14 дней**, затем удаляется |
| Адаптация (назначение, прогресс, попытки) | Удаляется сразу |
| Лента профиля | Удаляется сразу |
| Отпуска (`vacations.json`) | Хранятся **1 год** (в общем календаре не видны), затем purge |
| Идеи | **Бессрочно** (достояние платформы) |
| Обучалки / материалы, которые сотрудник сам написал | **Бессрочно** (как идеи); квест отпусков платформы — не контент сотрудника |
| Кошелёк | **1 год** (сейчас в localStorage браузера; срок заложен в denylist на будущее) |
| Покупки магазина | **1 год** (то же; каталог/товары не персональные) |
| Поля ФИО на оргсхеме + overlay manager | Очищаются сразу |

Админы (`account_role: admin`) в denylist не попадают. Отложенные чистки (аватар / отпуска) выполняются при обращении к API (не чаще раза в час).

## 10. База знаний

Страницы: `/knowledge` (поиск), `/knowledge/:id` (статья). Сейчас сид в `knowledgeBaseCatalog.ts`, живого RAG нет.

### 10.1. Два режима

| Режим | Что делает |
|-------|------------|
| Классика | По Enter ищет по названию и тексту. Выдача — ссылки: только название + подсветка совпадений, без сниппета. Истории запросов нет. |
| ИИ | Чат. Ответ человеческий, **в каждом ответе обязательны ссылки на конкретные статьи** (`useKnowledgeAiAnswer`, нельзя обойти). Фильтров нет. Диалог хранится 1 день (`vbi-kb-ai-chat-v1`). Переключение режима чат не сбрасывает. |

### 10.2. Классический поиск

- Нестрогое совпадение: часть слов может отсутствовать; ранжирование по попаданиям (заголовок весомее тела).
- Операторы: `"фраза"` — фраза целиком; `!слово` — строгое слово (не кусок другого); `OR` — или.
- Фильтры в UI сейчас выключены (`KB_FILTERS_ENABLED = false`), код не удалён. Поиск — по тексту, Enter / «Искать».
- Оценка разделов (кот): см. §10.4 — не только база знаний.
- Порции по 5, подгрузка при доскролле. В выдаче только актуальные статьи (устаревших в базе нет).
- Отдел — не фильтр на этом экране. Видимость (один / несколько отделов / всем) задаётся при редактуре статьи; сид сейчас = всей компании.

### 10.3. Редактура (позже)

Отдельная страница: автор статьи выбирает, кому видно — отдел, несколько или «Всем».

### 10.4. Кот оценки разделов

Разделы-кандидаты (если открыты по launch scope): `/knowledge`, `/vacations`, `/ideas`, `/vpn`, `/profile`.

| Правило | Как |
|---------|-----|
| Частота | Не чаще **1 раза в 60 дней** на пользователя (глобально, не на каждый раздел) |
| День | Свой у каждого (стабильный hash от user id внутри окна) — не всем в один день |
| Условие | В **текущем** разделе суммарно ≥ **1 час** активного времени (вкладка видима); тик 10 с |
| Трекер | В отзыве поле `page` + подпись раздела в админ-уведомлении и Bitrix |
| Хранение | `localStorage` `vbi-page-rating-gate-v1` (dwell + период показа/оценки) |

UI кота (ролик, бумажка, пузырь) — locked, см. `.cursor/rules/kb-rating-cat-edge.mdc`.

## 11. Как поддерживать этот документ

При изменении **бизнес-правила** (формула дней, этапы, что входит в баланс, лимиты, матчинг оргпанели, удаление сотрудника, поиск в базе знаний, правила кота оценки) — обновить соответствующий раздел здесь **в том же коммите**, что и код.  
`CHANGELOG` — кратко «что поменяли»; `PRODUCT` — актуальная правда «как сейчас устроено».
