## 1. График отпусков

Страницы: `/vacations` (сотрудник и руководитель), `/admin/vacations` (админ/HR).

### 1.1. Что можно сделать

| Роль | Возможности |
|------|-------------|
| Сотрудник | Выбрать даты → подать заявку; **скачать заявление** (`.docx`, только **ТД**, только после статуса **`approved`**); поставить **предварительную бронь** (месяц + длительность без точных дат); смотреть свой календарь и **общий** календарь команды (где доступно); править/удалять свои `pending` и согласованные, пока отпуск не полностью прошёл (**смена дат сбрасывает заявку снова в `pending`** — руководитель должен согласовать заново); пройти обучалку |
| Руководитель группы / отдела | Согласовать или отклонить заявки своей зоны (**очередь и счётчик — pending всех учётных лет**, не только выбранного года календаря); смотреть статистику команды; режим «как сотрудник» |
| Директор отдела (Digital и т.п.) | Второй шаг согласования для подчинённых групхедов; дневные счётчики отпускников по отделу |
| Admin / HR | Добавить отпуск сотруднику из графика (**заявка `pending`**, дальше обычная цепочка согласования); согласовать/отклонить из очереди `/admin/vacations` (по этапам, в т.ч. два шага Digital); rollover учётного года; полный обзор |

### 1.2. Статусы заявки

| Статус | Смысл |
|--------|--------|
| `pending` | На согласовании (есть ещё `approval_step`) |
| `approved` | Согласована |
| `rejected` | Отклонена |

**Отклонённые заявки не влияют на остаток дней.**

**Смена дат сотрудником:** если заявка была `approved` или `pending`, после сохранения новых дат она снова становится `pending` с шагом согласования с начала (руководитель / групхед). В календаре — рыжий статус, пока руководитель снова не согласует (тогда снова зелёный `approved`). HR/админ при правке чужих дат статус не сбрасывают.

### 1.3. Этапы согласования

Обычный отдел (один согласующий — руководитель из справочника):

```
подача → pending (manager) → approved | rejected
```

**Двухэтапные** отделы (сейчас: **Digital**, демо QA на localhost): сотрудник под **групхедом** (в Digital: Попов / Лунин / Цхай / Носков):

```
подача → pending (manager = групхед)
         → pending (director = директор отдела)
         → approved | rejected
```

**Полоски в «Мои заявки»:** всегда **3** сегмента одного размера (`Создана` → средний → `Согласована`). В Digital средняя полоска одна: сначала «У группхеда»; после ок группхеда кружок остаётся, полоска рыжая, текст «У директора»; после ок директора — все зелёные (как в обычном режиме). После создания заявки — шалфейный тост справа сверху с дисклеймером про билеты (без полосок в тосте).

- Самосогласование **запрещено**: согласующий не может утвердить свою же заявку.
- **Задним числом** (дата начала раньше сегодня): может только **admin** («+ Добавить отпуск» в `/admin/vacations` или правка дат). Сотрудник, руководитель и HR — нет; на сервере создание/правка с прошлым `start` отклоняется.
- Заявка **директора отдела** в двухэтапном отделе идёт к его руководителю (`manager`), не к самому себе на шаге director.
- У **генерального директора** (`manager` пустое — так и должно быть: он никому не подчинён) заявку согласуют **admin/HR** из админки; отдельного «руководителя над гендиром» в справочнике нет.
- **Ручное добавление admin** («+ Добавить отпуск» в `/admin/vacations`): создаётся обычная заявка `pending` с тем же `approval_step`, что при подаче сотрудником; уведомление уходит текущему согласующему. Admin/HR может согласовать из панели «Заявки на согласование» **по этапам** (для Digital под групхедом — сначала шаг manager, затем director). Мгновенного `approved` после создания нет. Обход лимита месяца (§1.8) и пересечения групхедов (§1.9) и **прошлых дат** — только для **admin** при создании/правке.
- После финального `approved` — синк отсутствия в Bitrix (пальма), если настроен вебхук/OAuth (см. `BITRIX.md`).
- Смена дат у согласованной заявки — обновляет отсутствие в Bitrix; отклонение или удаление — снимает пальму.
- Если синк с Bitrix не удался (создать / обновить / снять) — уведомление админу в колокольчике платформы.

Уведомления: в платформе (колокольчик сотрудника/руководителя) и параллельно в Bitrix **`im.notify.system.add`** (без личных чатов для согласования).

### 1.3.1. Напоминания от чат-бота Bitrix (не согласование)

Канал: бот **VBI HR** (`imbot.message.add`, `BITRIX_IMBOT_ID=2830`). Подробности и установка timers: **[BITRIX.md](./BITRIX.md)**.

| Кому | Когда (МСК) | Что |
|------|-------------|-----|
| Сотрудник | проверка **каждый день в 12:00**; письмо **один раз** | `approved`, старт **ровно через 21 день** → заявление + передача проектов; для Digital / SEO·ORM — ссылка на памятку отдела |
| Руководитель | **1-е в 11:15** | `approved` со стартом **в текущем месяце** (учесть отсутствие) |
| Руководитель | **15-е в 11:15** | `approved` со стартом **в следующем месяце** (спланировать передачу дел) |

**Зоны руководителя:** Ревзина — весь Digital; Музыка / Трубицына / Волдайский / Малиновская / Лашин — весь свой отдел (у Лашина — Отдел продаж); групхеды и прочие — только прямые подчинённые. **Юдин Вадим не получает** эти сообщения.


### 1.4. Как считаются дни отпуска (длина периода)

Формула: **календарные дни от `start` до `end` включительно, минус официальные праздники РФ** из производственного календаря платформы.

| Учитывается | Не учитывается |
|-------------|----------------|
| Будни | Праздники из списка года (`isRuHoliday`) |
| **Выходные (сб/вс)** — входят в счёт | |

Код: `countVacationBillableDays` / `countVacationBillableDaysInYear` в `vacationCalendar.ts`.  
Календари **2026** и **2027** зашиты в том же файле (праздники + переносы длинных каникул); для других лет без списка праздники = 0 исключений.

Заявка через Новый год лежит в папке года **даты начала**, но в баланс каждого учётного года входят только billable-дни, попадающие в этот календарный год (хвост января списывается из баланса следующего года, а не «теряется»).

Пример: 1–7 янв при новогодних каникулах в списке — в счёт попадут только дни **вне** праздничного набора.

### 1.5. Остаток дней отпуска (баланс)

**Смена года = обычная смена месяца.** Остаток один, непрерывный: начисления идут помесячно, отпуска списываются, и 31 декабря → 1 января ничем не отличается от 31 мая → 1 июня. Ни одна цифра не обнуляется и не пересчитывается при смене года; долг (отрицательный остаток) переходит дальше как есть. Учётный год (`primaryYear`) и переход года нужны только хранилищу: от какой даты ведётся `vacation_opening_balance`.

**Начисление:**

1. Точка отсчёта: остаток на 1 января `primaryYear` (`vacation_opening_balance`; если не задан, оценка по модели ЗУП от даты найма). Переход года сдвигает точку отсчёта на год и записывает туда ровно то, что было доступно на 01.01, поэтому цифры не меняются.
2. Плюс помесячные начисления по модели ЗУП (норма **28 дней/год**, событие начисления раз в месяц от даты найма, точность 0,1), в любом году подряд.

**Списывается:** billable-дни заявок `approved` и `pending` (любого года). Не списываются `rejected`, предварительные брони, прочее.

**Цифры в правой панели (и в профиле, мобильной шапке, у руководителя):**

| Цифра | Определение |
|-------|-------------|
| **Доступно дней отпуска** | Остаток на сегодня (точка отсчёта + начисления по сегодня − `approved` и `pending` дни по сегодня) **минус все запланированные дни после сегодня** (`approved` и `pending`, в любом году). Так было и раньше для будущих отпусков текущего года (декабрьский отпуск в октябре уже вычтен); отпуск на 2027 вычитается точно так же. Может быть отрицательным (долг), показывается как есть, например `-3`. Округление вниз до 0,1. |
| **Отгулял** | Прошедшие дни согласованных отпусков (по сегодня включительно), за все годы, что есть в платформе. |
| **План** | Будущие дни согласованных отпусков (после сегодня) + все дни заявок на согласовании, в любом году. |
| **«Рассчитать доступные дни к дате»** | Остаток на выбранную дату: начисления по эту дату − `approved` и `pending` дни по эту дату (без отпусков после неё). |

Пример: на 19.10.2026 остаток 23,6, заявлено на 2027 год 24 дня → «Доступно» −0,4, «План» 24; «к дате» 31.07.2027 = 23 (за 9 месяцев начислится ещё около 21 дня).

- **Долг переносится:** −3 на 31.12.2026 → −3 + 2,3 = −0,7 на 31.01.2027, −3 + 9,3 = 6,3 на 30.04.2027. Переход года записывает −3.
- В «Мои заявки» видны заявки всех лет, брони текущего и следующего года.

### 1.6. Проверка «хватит ли дней» при выборе дат (аванс)

Перед подачей считается доступный остаток **на дату начала** выбранного периода (`calcAvailableOnDate`):

- начисление к дате начала;
- минус `approved` и `pending` **по дату начала** (не весь будущий хвост после неё в этой проекции).

Если нужных billable-дней больше, чем доступно → статус **аванс** (можно подать, но UI предупреждает).  
Проекция «к прошлой дате» для будущего баланса не должна завышать текущий остаток: для UI «расчёт к дате» имеет смысл на **будущие** даты.

### 1.7. Учётный год

| Понятие | Смысл |
|---------|--------|
| `primaryYear` | Учётный год ЗУП: база остатка на 01.01 этого года |
| Год в UI / `requestsByYear` | Папка календаря; заявка кладётся в год **даты начала** |
| Архивные годы | У сотрудника — просмотр; правки в прошлом году ограничены |

Переход года: остаток на 31.12 → новый `vacation_opening_balance`, `primaryYear` += 1 (`vacationYearRollover`). **Делается автоматически 1 января в 00:00 по Москве** (если сервер в полночь не работал, то сразу после запуска). Руками ничего делать не нужно; кнопка/API для admin/HR осталась на крайний случай, повторный запуск ничего не задваивает. Заявки, поданные в момент перехода, не теряются.

**Бронь и заявки на следующий год:**

- Новые заявки, новые даты заявки и брони можно оформить только на **текущий учётный год** и **следующий** (в 2026: на 2026 и 2027). Попытка на 2028 → «Отпуск можно оформить только на 2026 или 2027 год…» (для брони: «Бронь можно поставить только на…»). Уже существующие заявки прошлых лет правятся и удаляются как раньше (без переноса в недоступный год).
- Отпуск может переходить через Новый год (например, 28.12.2026–10.01.2027): заявка лежит в году начала, а в календаре видна в обоих годах; пересечение со своим отпуском ловится и при просмотре следующего года.
- **Хватит ли дней** для отпуска в следующем году: остаток непрерывный, январь это просто следующий месяц. Доступно на дату в 2027 = то, что было доступно на 31.12.2026 (после всех `approved` и `pending` 2026), плюс стандартные помесячные начисления января…месяца даты (включая начисление 1 января, если у сотрудника оно на 1-е число), минус `approved` и `pending` 2027 по эту дату. Пример: на 29.12.2026 доступно 5 дней → на 05.04.2027 будет 5 + 7 = 12, на 30.04.2027: 5 + 9,3 = 14,3. Ровно это значение переход года записывает в `vacation_opening_balance` на 01.01. Одинаково считают форма заявки, «Рассчитать доступные дни к дате», очередь руководителя и админка.

### 1.8. Предварительная бронь

- Месяц + длительность (1–28 дн.), **без** точных `start`/`end`.
- **Не** влияет на остаток и согласование.
- В календаре — полосатая плашка; «Уточнить даты» → обычная заявка.
- Нельзя создать бронь в прошедшем месяце и в **последний день** месяца брони.
- **Лимиты (Digital / демо QA):** слот месяца = **бронь или заявка** (`pending`/`approved`) на этот месяц.
  - **Отдел:** до **5** человек на весь Digital — считается по-прежнему «коснулся месяца хоть одним днём» (месяц целиком, без учёта точных дат).
  - **Подгруппа:** не более **1** человека внутри подгруппы **одновременно по реальным датам** (с 2026-10-15; до этого считалось как отдел — «месяц занят», что ложно блокировало не пересекающиеся по датам отпуска). Для заявок с точными датами (`start`/`end`) лимит смотрит настоящее пересечение дней: если у Маши отпуск 26 окт – 1 ноя, а Коля подаёт на 9–22 ноя — даты не пересекаются, Коля не блокируется; если бы Коля подал на 30 окт – 5 ноя — пересечение есть (30–31 окт, 1 ноя), блок сработает. Для **брони** (только месяц+длительность, без точных дат) настоящего пересечения посчитать нельзя — она по-прежнему консервативно занимает весь месяц целиком, независимо от того, проверяется бронь сама или против неё проверяют чужую заявку.
  - При исчерпании лимита `+бронь` недоступна, новую заявку/бронь на этот месяц (отдел) или пересекающиеся даты (подгруппа) тоже нельзя. Уже существующие записи не пересчитываются задним числом.
  - **Исключение (locked):** у группы **Цхай Виталий** (`digital-tskhai`) нет лимита подгруппы вообще (ни по месяцу, ни по датам), но лимит **5 на отдел** действует как у всех — их слоты входят в общий пул.
  - **Админ** из «+ Добавить отпуск» в `/admin/vacations` может поставить отпуск в обход лимита месяца/подгруппы (как и правило групхедов в §1.9).

### 1.9. Доп. правила Digital

- **Групхеды:** не более одного групхеда в отпуске на пересекающиеся даты (`pending`/`approved`); иначе предупреждение в форме и отказ сервера (409). **Админ системы** может поставить или сдвинуть отпуск в обход этого правила (предупреждение в UI остаётся).
- **Свой отпуск:** два периода одного сотрудника (`pending`/`approved`) не могут пересекаться по датам — блок в UI и отказ API (409). Действует и для admin при ручном добавлении.
- Пересечения отпусков коллег в UI подсвечиваются (информативно), отдельный жёсткий запрет — только правило групхедов и «свой vs свой» выше.
- Владение заявкой/бронью (правка, удаление): по `employee_id` справочника; ФИО — только fallback для legacy без id.

### 1.10. Обучалки

- Сотрудник: квест по календарю/заявке (`useVacationTraining`).
- Руководитель: свой квест (`useManagerVacationTraining`).
- Ачивка «Календарь отпусков» у руководителя — после **обоих** квестов.

### 1.11. Памятка после отпуска

После **согласованного** отпуска ≥ **7** календарных дней: при первом входе **после** последнего дня отпуска, но не позже **7 рабочих дней** (производственный календарь РФ), показывается карточка «С возвращением!» в стиле **Design C**: вытянутая lavender-карточка (`#c8bddc`, AR как series-c ≈ 879∶1279, все углы скруглены `--pvm-radius`) с paper-grain, сцены маскота Vibe отдельно (`/memos/pvm-c-art-*.png`, без текста в растре), UI-текст из `postVacationMemoSlides.ts`. Навигация только кнопками (Позже/Прочитать, Назад/Дальше/Спасибо) и свайпом; нумерованных folder-tabs сверху нет. **Прочитать** открывает карусель сразу с **совета 1** (без вводной). **Позже** сворачивает карточку в чип в правом нижнем углу на **10 рабочих дней**; клик по чипу / уведомлению (`?pvm=tips`) открывает вводную «Вот четыре совета», затем 4 совета. После прочтения до конца чип пропадает; welcome **не повторяется** для той же `requestId` (фаза `done` в `vbi-post-vacation-memo-v2`). В уведомлениях запись остаётся. Превью на localhost/стейдже: `?pvm=1`. Ключ `vbi-post-vacation-memo-v2`.

### 1.12. Сохранность данных

Рабочий файл: `server/data/vacations.json` (заявки всех статусов, брони, лимиты). При деплое **не перезаписывается**.

Раз в неделю (воскресенье 03:00 МСК) systemd делает снапшот в `server/data/backups/vacations/vacations-YYYY-MM-DD.json`. Хранятся **12** последних недель. Восстановление: скопировать снапшот обратно в `vacations.json` и перезапустить `vbi-hr`.

## 2. Банк идей

Страницы: `/ideas` (сотрудник), `/admin/ideas` (admin/HR). Плитка на профиле ведёт в банк идей.

Очередь общая на сервере (`ideas.json`): идеи и голоса видят все сотрудники, браузеры друг друга не перезаписывают. Стартовый список пустой (без демо).

### 2.1. Возможности сотрудника

- Предложить идею (категория, город, описание, **файл** png/jpg/pdf/doc/xls/ppt до 12 МБ). Файл хранится на сервере; плашка «файл» открывает вложение. Категории: Офисная среда, Процессы, Культура, IT и инструменты, Корпоративы и развлечения, Другое. Старое имя «Благополучие» при чтении очереди переименовывается.
- Голосовать 👍/👎.
- Фильтры (все/мои, категория, статус), поиск, сортировка (новые / старые / популярные / непопулярные).
- Цветные плашки сводки переключают фильтр статуса в тулбаре (без отдельной подсветки плашки).
- Удалить **свою** идею (в банке сотрудника). Чужие идеи сотрудник не удаляет — даже если зашёл под админом в режим «Сотрудник». Админ/HR удаляют любые идеи только из `/admin/ideas`.
- Видеть комментарий админа к этапу (в т.ч. причину отклонения).

### 2.2. Этапы идеи

```
отправка
  → На рассмотрении (review)
       ├─→ Реализация (implementation)
       │      └─→ Реализовано (done)
       └─→ Отклонено (rejected)   ← обязателен комментарий с причиной
```

| Переход | Кто | Подтверждение | Комментарий |
|---------|-----|---------------|-------------|
| Создание → review | Сотрудник | — | — |
| Смена этапа | Admin / HR | Модалка подтверждения | Необязателен; при **отклонении — обязателен** (≥3 символа) |
| → Реализовано | Admin / HR | Модалка | Необязателен |

После создания: уведомление admin/HR (`idea_submitted`) → колокольчик, ссылка на `/admin/ideas`.

**При каждой смене этапа** автору идеи:
- уведомление в платформе (`idea_status_changed`, колокольчик сотрудника → `/ideas`);
- системное уведомление в Bitrix (`im.notify.system.add`, ссылка на `/ideas`); в текст попадает этап и комментарий (если был).

Админ может удалить любую идею.

### 2.3. Статистика и топ-авторов

- Счётчики у сотрудника (всего / по статусам) — по его идеям.
- **Топ-авторы:** только идеи со статусом **Реализовано** (`done`).
- Подпись в топе: «N реализованных идей» (N пересчитывается при каждом `done`; позиции в рейтинге меняются при необходимости).
- Голоса и идеи на рассмотрении / в реализации / отклонённые **не** увеличивают место в топе.

## 7. Профиль — ачивки и недавняя активность

На своём `/profile`:

1. **Ачивки** — до 2 рядов иконок без подписей; полный каталог в оверлее «Все».
   - **Превью блока «Ачивки»** — только **полученные**; «Календарь отпусков» первым (круглый PNG). Неполученные — только в оверлее «Все · N». Под ФИО — до 5 (без квеста).
   - **Выдача автоматически:** стаж 1 год по `hired_at`; 5/10/15 после claim юбилея (+ купон); ≥28 согласованных дней отпуска за учётный год; реализованные идеи; покупки в магазине (каталог + юбилейный заказ, **не** ручная лента).
   - **Выдача вручную** (`/admin/activity`): `talk`, `learning`, `promotion`, `mentor`, `practice`.
   - **Лучший специалист продаж** (`sales-best-1`…`5`): админ выбирает на `/admin/sales-best` (напоминание в колокольчик **29-го** МСК). Лучший — кто выше всех перевыполнил план. Ачивка в профиле только с **первого рабочего дня** следующего месяца (`reveal_on`, код + производственный календарь РФ) — до этого победитель скрыт. Перевыбор до reveal разрешён. В день reveal — запись в **Недавнюю активность** и **Новости коллег**.
   - **Оверлей «Все»** — 7 секций: Стаж и карьера · Отпуск · Выступления и кейсы · Обучение · Магазин · Лидерство и инициатива (идеи, наставник, практика, лучший ОП) · Корпоративная культура (Pit Stop топ‑3).

   - Журнал (`journal-*`) — пока без источника.
2. **Недавняя активность** — лента событий; **новые сверху** (сортировка по `occurred_at`).
3. **Команда** — коллеги (без себя):
   - сотрудник — весь отдел;

   - Демо-проверка без Bitrix: `alina@vbi.local` — весь отдел «Тестировщики».
   - Блок фиксированной высоты (как «Недавняя активность»): длинный список скроллится **внутри** карточки, страница не растёт.

| Коллег в блоке команды | Слева | Справа |

## 9. Удаление сотрудника из справочника Vibe

### 9.1. Кто может войти

Вход в платформу — **только** для людей из справочника «Сотрудники» (`employees.json`).

- OAuth Bitrix успешен ≠ доступ в Vibe: если пользователя нет в справочнике (экстранет, практиканты, гости портала) — **403**, сессия не создаётся.
- Уже выданная Bitrix-сессия на каждом API-запросе перепроверяется: нет в справочнике → cookie сбрасывается.
- Удалённые из справочника — denylist + тот же отказ (см. ниже).
- Синк при входе / кнопка «синхронизировать из Bitrix» **обновляет** уже заведённых, **не импортирует** новых ACTIVE с портала.
- Демо-логин/пароль на **production** отключён (API и UI).
- **Вход по паролю Vibe** (`POST /api/auth/vibe-login`): логин = **email** из справочника (допускается локальная часть до `@`). HR задаёт email и пароль в Админ → Сотрудники (кнопка 🔑, модалка «Логин + пароль»); хеш пароля — `server/data/vibe-passwords.json`.

### 9.1.2. Поля справочника в админке

Страница `/admin/employees` — единый источник кадровых атрибутов для платформы (`employees.json`).

| Поле | Ключ JSON | Источник |
|------|-----------|----------|
| ФИО, должность, отдел | `name`, `title`, `department` | Bitrix синк (имя/должность — уведомление при расхождении) + ручная правка |
| Руководитель | `manager` + `manager_id` | ФИО для UI; иерархия/календарь/согласование — по `manager_id`. Overlay `employee-managers.json` хранит ФИО; id проставляется при чтении |
| Дата приёма | `hired_at` | Ручная / при импорте из Bitrix (`DATE_REGISTER`) |
| Bitrix ID | `bitrix_user_id` | Ручная / синк |
| Роль доступа | `account_role` | Ручная |
| **Юр. лицо** | `legal_entity` | Ручной выбор в админке: **Высокие Бизнес Идеи**, **ВиБиАй** (не из Bitrix). Устаревшее `Высокие` в JSON маппится в полное имя в заявлении |
| **Форма договора** | `contract_form` | Ручной выбор в админке: **СЗ**, **ТД** (не из Bitrix) |

Пустые `legal_entity` / `contract_form` допустимы. Синк Bitrix поля не перезаписывает и не заполняет.

**Вход Vibe без Битрикса:** сотрудник в профиле (шестерёнка у ФИО) видит логин и пароль; глаз — показать/скрыть текст, карандаш — правка. «Сохранить» / «Отмена» только в режиме правки. HR задаёт то же в Админ → Сотрудники (🔑). Для входа — scrypt-хеш; для показа себе — AES-seal рядом (`vibe-passwords.json`), не в Битриксе.

**Заявление на отпуск** (locked): кнопка «Скачать заявление» (`.docx`) видна **только при всех трёх условиях**:

1. Статус заявки **`approved`** (Согласовано).
2. Отпуск ещё не начался: **`start > сегодня`** (в первый день отпуска и позже кнопки нет).
3. У сотрудника в справочнике **`contract_form === 'ТД'`** (для СЗ и пустого договора — нет).

UI и API проверяют одинаково; иначе 403. В документ: юр. лицо, должность, полное ФИО, даты `с … по … на N дней`, дата выхода; вид отпуска в бланке зафиксирован как «ежегодный оплачиваемый отпуск».

**Привязка отпусков:** заявки/брони хранят `employee_id` (id справочника) + строку ФИО; сопоставление с сотрудником — по id, ФИО только fallback.

**ФИО в UI:** полное (фамилия, имя, отчество) — **только в админке** (справочник сотрудников и др.) и в **заявлении на отпуск**. Везде остальном (профиль, топбар, визитка, **оргсхема / панель отдела**, календари отпусков, очередь согласования у руководителя, идеи, база знаний, кошелёк, ответы Афины по оргструктуре) — **фамилия + имя** (`formatEmployeeShortName`: при 3+ словах берутся первые два). Сопоставление заявок и сессии со справочником — `employeeNamesMatch` (точное или по фамилии+имени).

### 9.1.1. Сессия и безопасность входа

| Мера | Как сейчас |
|------|------------|
| TTL cookie | **8 часов**, скользящее продление при активности (если осталось < 4 ч) |
| Secure | `Secure`, если `APP_PUBLIC_URL` / redirect на **https** (или `VBI_COOKIE_SECURE=true`); на текущем HTTP-бою флаг не ставится, иначе cookie не прилипнет |
| Подпись | HMAC-SHA256 (`VBI_SESSION_SECRET` или производная от `BITRIX_CLIENT_SECRET`); сырой JSON без подписи не принимается |
| Справочник | Bitrix OAuth без записи в employees → 403; сессия на каждом API перепроверяет roster/denylist |
| XSS | CSP (default-src self + Метрика/шрифты), без `v-html` на пользовательских строках, HTML в идеях срезается при сохранении |
| Секреты | `BITRIX_CLIENT_SECRET` / webhook только server runtimeConfig (не `public`); webhook в логах редактируется; oauth-debug только localhost |

### 9.2. Что происходит при удалении

Удаление из «Сотрудники» **сразу закрывает доступ**: запись в denylist (`employee-access-denylist.json`), сессия сбрасывается при следующем API-запросе, повторный вход через Bitrix/демо отклоняется. Синк Bitrix и merge при деплое **не возвращают** удалённого в справочник, пока его снова не добавят вручную (тогда denylist снимается). Список API тоже фильтрует denylist.

| Данные | После удаления |
|--------|----------------|
| Справочник / общий календарь команды / панель оргсхемы | Нет в списках |
| Доступ (сессия, логин) | Закрыт сразу |
| VPN-ключи | Удаляются в учёте платформы **и** в панели wg-easy; если удалить пир не удалось — уведомление админу `vpn_peer_delete_failed` |
| Уведомления сотрудника | Очищаются сразу |
| Аватар | Живёт **14 дней**, затем удаляется |
| Адаптация (назначение, прогресс, попытки) | Удаляется сразу |
| Лента профиля | Удаляется сразу |
| Отпуска (`vacations.json`) | Хранятся **1 год** (в общем календаре не видны), затем purge |
| Идеи | **Бессрочно** (достояние платформы) |
| Обучалки / материалы, которые сотрудник сам написал | **Бессрочно** (как идеи); квест отпусков платформы — не контент сотрудника |
| Кошелёк | **1 год** (сейчас в localStorage браузера; срок заложен в denylist на будущее) |
| Покупки магазина | **1 год** (то же; каталог/товары не персональные) |
| Поля ФИО на оргсхеме + overlay manager | Очищаются сразу |

Админы (`account_role: admin`) в denylist не попадают. Отложенные чистки (аватар / отпуска) выполняются при обращении к API (не чаще раза в час).

### 10.0a. Статьи сотрудников и модерация руководителем

На `/knowledge` — круглая FAB с карандашом **слева внизу** (правый нижний угол занят котом оценки / памяткой): крем + чёрная рамка, лайм только на hover. Ведёт на **`/knowledge/write`** — отдельная страница в том же паттерне, что `/admin/knowledge` (редактор + списки), без модалки поверх поиска.

| Роль | Что видит / делает |
|------|---------------------|
| Сотрудник | Только **свои** статьи. Создаёт → `pending_review`. Пока на проверке — **нельзя править**. Черновик (`draft`) и «На доработку» (`revision_requested`) — можно править и снова отправить. Правка **опубликованной**: живая версия не меняется; текст уходит в `pendingRevision`, после «Принять» заменяет опубликованную. Аудитория: «Вся компания» (`departments: []`) или выбранные отделы. |
| Руководитель | Свои + статьи **прямых** подчинённых (поле `manager` в справочнике). Кнопка **«Проверить»**: режим ревью, инлайн-комментарии (выделить текст → ПКМ «Оставить комментарий»; на мобиле — кнопка после выделения), сайдбар справа. Действия (пилюли): **Принять** → `published`, автор = сотрудник, `approvedAt` = дата принятия; **На доработку** → автору с комментариями; **Отклонить** → `rejected` навсегда, модалка по центру с затемнением, **причина обязательна**. |
| Админ | `/admin/knowledge`: те же действия модерации (Принять / На доработку / Отклонить) для любой статьи. |

**Статусы:** `draft` \| `pending_review` \| `published` \| `revision_requested` \| `rejected`. Legacy `review` при чтении = `pending_review`. RAG / `GET /api/knowledge` / ИИ — **только `published`**.

**Уведомления** (колокольчик Vibe + Bitrix `im.notify.system.add` через OAuth, не чат):

1. Руководителю при отправке: «Ваш сотрудник подготовил материал для статьи в Базу знаний…»
2. Автору при принятии: «Поздравляем! Ваша статья прошла проверку и опубликована…»
3. Автору при доработке: «К сожалению, подготовленный материал не прошел проверку…»
4. Автору при отклонении: «Материал отклонён и закрыт. Причина: …»

Если у сотрудника нет руководителя в справочнике — отправка сохраняется, notify руководителю пропускается (лог warning).

API сотрудника: `GET /api/knowledge/articles/mine`, `POST /api/knowledge/articles`, `PATCH …/:id`, `POST …/:id/submit`, `POST …/:id/moderate`, `POST …/:id/comments`.

### 10.0. Поиск по смыслу (RAG) — целевое устройство ИИ

**Зафиксировано:** ответы режима «Спросить ИИ» подбирают статьи **по смыслу вопроса**, а не по совпадению отдельных слов.

Как должно работать:

1. Опубликованные статьи режутся на фрагменты и получают числовые «отпечатки смысла» (эмбеддинги Yandex Cloud, тот же folder, что у GPT).
2. Вопрос сотрудника тоже переводится в такой отпечаток; дополнительно — **осторожная переформулировка** и **словесный слой** (гибрид смысл+слова; словоформы вроде «уволиться» ≈ «увольнение», плюс явные синонимы; не путать разные слова с общим началом вроде «привет» / «приветствие»). Приветствия и «спасибо» **не ищутся** по статьям. Опечатки и сокращения в чате нормализуются до поиска (очепятка→опечатка, еком→ecom). **Кейсы ecom** (клиентские case studies): статьи `kb-case-ecom-*` + обзор `kb-case-ecom-index` (company-wide, published; MD-источник `docs/knowledge-cases/ecom/`). Вопрос с «кейс/кейсы/case study» / ecom идёт через RAG (stub «не умею работать с кейсами» снят). Ответ для продаж: при сужении по каналу (SMM/таргет/посевы) — если прямых кейсов нет, явно «по [канал] пока не добавлены», затем близкие с указанием каналов из статьи; 1–3 похожих подробно, короткий список остальных ecom, папка Bitrix кейсов; **без URL в тексте** — ссылки только в «Ещё по теме» (`sanitizeKbAiAnswerText`). Промпт в `yandexGpt.ts`, буст в `applyCaseEcomScoreAdjust` / `applyCaseChannelScoreAdjust` / `knowledgeRag.ts`. Уточнения по кейсам в диалоге (`isKbCaseOrChannelFollowUp`) склеиваются с прошлым вопросом, модель не повторяет verbatim список. **авто ≠ Авито:** «авто / автотематика / машины» — автомобильный сегмент, не маркетплейс; статья `[Специалисты] Авито…` (`kb-30126`) не поднимается на такие вопросы (`shouldSuppressAvitoForAutoQuestion`); «авито/avito» — наоборот про площадку. Двусмысленные внутренние термины (напр. «дейоф» = отгул *или* SaaS DayOFFF; «доступы» / «афина» = AFINA CRM, гостевые кабинеты или памятка отдела продаж) разбираются по **общему смыслу** вопроса: при ясном сигнале — **одна** статья; при сомнении («просто доступы» / «что такое дейоф») бот даёт **два коротких ответа** и просит уточнить. **Отпуск:** Digital видит Bitrix `kb-21301` **и** Vibe `kb-vibe-vacations-digital`; SEO — Bitrix `kb-24611` **и** Vibe `kb-vibe-vacations-other`; прочие отделы — `kb-vibe-vacations-other` (своего Bitrix-регламента нет). Без слова отдела в вопросе sense берётся из `department` сессии; чужие department-статьи не попадают (фильтр аудитории). Регламент **UTM** / когда UIS·Roistat·Calltouch — статья `kb-23420`, не гостевые доступы и не «Контакты». **Акты** от РП (Яндекс / VKR / SMM) — `kb-31980`, не блок «Яндекс» в Контактах. **Списания** в AFINA (комиссии / прочее) — `kb-28468`, не «доступы к афине». В чате — **память** последних реплик: уточнения («а подробнее?», «это все?», «напиши ещё другие…», «а остальные?») склеиваются с прошлым рабочим вопросом для RAG и GPT; ложный OFFTOPIC на таких уточнениях при найденном контексте отбрасывается (остаток списка из того же блока или «в статье больше нет»). Явный оффтоп (погода, шутки) по-прежнему отказ без статей.
3. В контекст модели попадают ближайшие по комбинированному score фрагменты (и статьи), даже если формулировка другая («отпуск раньше» ≈ «аванс»). У длинных статей (например «Контакты», гостевые доступы, регламент UTM, акты РП, списания AFINA, DayOFFF) в контекст идёт блок под термин вопроса (Programmatic, юристы, «Доступ к Директ», коллтрекинг UIS/Calltouch, YDirect / VKR, Прочее PPC и т.п.), а не чужой кусок той же статьи; случайное слово в другой статье (DayOfff / список PPC / регламент дизайна / найм при «регламент utm») не перебивает — учитывается короткая шапка секции и интент («кому писать / контакты», UTM-тегирование, акты, списания). Статья видна: **всем** (общие) или **только отделам** из поля `departments` (как иерархия «Общие по компании» / отдел). На карточке и в статье — шильдик отдела. Статьи про отпуска в Vibe разделены: Digital (`kb-vibe-vacations-digital`) и остальные отделы (`kb-vibe-vacations-other`); общей «Всем» нет. По отпуску в контекст кладутся **оба** релевантных источника (Bitrix + Vibe), модель должна объединить их в один ответ.
4. Модель отвечает **только по этому контексту**; ссылки «Ещё по теме» — сначала статьи-источники ответа (`usedSourceIds`), затем похожие RAG-хиты. Если Yandex падает — пользователю «Бот ушёл на перекур…», админу алерт, ответ упрощённый.
4a. **Оргструктура отдельно от статей:** вопросы «кто руководит отделом…», «кто гендир», состав отдела, **конкретный сотрудник по ФИО** — ответ из `org-structure.json` / справочника сотрудников, **без** RAG/Yandex. Рядом с ФИО — квадратик Bitrix ↗ (как в визитке). В «Ещё по теме» — ссылка **Структура** на сотрудницкую `/organization` (не админский редактор).
5. Индекс смысла хранится на сервере (`server/data/knowledge-rag-index.json`), пересобирается при сохранении/публикации статей и при необходимости по запросу админа.
6. Проверка качества: кейсы на перефразах (`knowledgeRagEvalCases.ts`, в т.ч. `expectAll` Bitrix+Vibe), прогон `POST /api/admin/knowledge/rag-eval`; локально — `scripts/knowledge/check-rag-contacts.mjs`, `check-rag-access-utm.mjs`, `check-rag-dayoff-acts-writeoffs.mjs`, `check-rag-vacation-dual.mjs`, `check-rag-rewrite-safety.mjs`, `check-kb-dialog-followup.mjs`, `check-kb-cases-fallback.mjs`, `check-kb-auto-avito.mjs`.

Список статей `GET /api/knowledge` — **только под сессией** и с фильтром по отделу.

Классическая вкладка «Поиск» пока остаётся **по словам** (удобно для точного названия / операторов `"фраза"`, `!слово`). Имеет смысл позже тоже усилить смыслом — отдельная задача. Фильтр по отделам — жёсткое разделение данных (позже), не через нейроранжирование.

### 10.1. Два режима

|-------|------------|

### 10.2. Классический поиск

- Нестрогое совпадение: часть слов может отсутствовать; ранжирование по попаданиям (заголовок весомее тела).
- Операторы: `"фраза"` — фраза целиком; `!слово` — строгое слово (не кусок другого); `OR` — или.
- Фильтры в UI сейчас выключены (`KB_FILTERS_ENABLED = false`), код не удалён. Поиск — по тексту, Enter / «Искать».
- Оценка разделов (кот): см. §10.4 — не только база знаний.
- Порции по 5, подгрузка при доскролле. В выдаче только актуальные статьи (устаревших в базе нет).
- Отдел — не фильтр на этом экране. Видимость (один / несколько отделов / всем) задаётся при редактуре статьи; сид сейчас = всей компании.

## 10a. Pit Stop 14 — гонки (`/event/pit-stop`)

- Каждый сотрудник катается сам; результат — **лучший круг** (одна строка на человека в «Тайминге», сортировка по времени, при равенстве — кто раньше проехал).
- Заезд — **1 круг**; после финиша таймер останавливается; новый заезд — пробел / тап по карте (телефон) / «На старт», затем countdown **3–2–1–Поехали!**. Поздравление на трибунах и триумф-звук — **только если улучшили рекорд**. На телефоне — лёгкая вибрация при ударе о бортик и при рекорде.
- Звуки (синтез Web Audio, без внешних файлов): разгон, визг в повороте, тихий удар о бортик, аплодисменты при рекорде — `events/pit-stop-14/raceAudio.ts`.
- «Тайминг»: топ‑3, ниже остальные; снизу всегда закреплена строка пилота (место + время). Обновляется срезами по Москве в **10:00, 12:00, 14:00, 16:00, 18:00, 20:00, 22:00 и 00:00**; с 00:00 до 10:00 таблица не меняется. Свой текущий рекорд пилот видит сразу (HUD + плашка «попадёт в таблицу в …»).
- **Стоп ивента: 10 октября 03:00 МСК** — новые круги не принимаются, флаг в сайдбаре скрывается, на хабе остаётся итоговый тайминг (срез на момент стопа). Ачивка **`pit-stop-14`** («Легенда трека — 14») — топ‑3 по итогам; секция «Корпоративная культура»; видна на визитке коллеги. Фиксация winners лениво при первом запросе после стопа.
- **Страница итогов: 10 октября 10:00 МСК** — трасса/гараж заменяются статичным подиумом (`winners-podium.jpg` + аватары топ‑3 в кругах); рейтинг остаётся справа без строки «Обновлено…». На **стейдже** экран итогов показывается сразу (превью). Между 03:00 и 10:00 на бою — оверлей «Финиш ивента» на трассе.
- При первом входе енот объясняет правила (5 реплик); повторно — кнопка «Енот» (на экране итогов не показывается).
- Круг: старт таймера при первом пересечении линии старта на восток; засчитывается следующее пересечение, если пройдены все 5 контрольных зон трассы. Пересечение против хода сбрасывает текущий круг. «На старт» / R — болид на спавн + countdown.
- Сервер принимает круг от **8 с** до **10 мин**; быстрее — 400 «Круг не засчитан». Худший круг рекорд не перезаписывает, но увеличивает счётчик кругов и обновляет цвет болида в таблице.
- **Античит (бот за рулём):** при заходе на хаб выдаётся `raceToken` (~2 ч); без него круг не пишется. С кругом уходит компактная телеметрия (клавиши/`isTrusted`, стик, путь, зоны, удары о борт). Сервер считает score подозрения; при пороге ставит флаг на рекорд. Круг **всё равно засчитывается**; публичный тайминг не меняется. Разбор — `/admin/quest-dashboard` (блок «Подозрение на бота»: Снять / Подтвердить).
- Цвет болида — выбор в «Гараже» (7 вариантов), хранится в браузере.
- Квест с чек-поинтами (8 этапов) с хаба скрыт, код и данные `pit-stop-14.json` не удалены.

## 10b. Опросы (`/admin/surveys`, публично `/s/:slug`) — Phase 1

Внутренний конструктор опросов (аналог webask.io), фаза 1 — MVP. Детали путей/схемы данных — в `CHANGELOG.md` (запись 2026-10-13) и `ARCHITECTURE.md`.

- **Создатель** (роль admin/hr, внутри Vibe): собирает опрос из 9 типов вопросов (информационный блок, выбор одного, выбор нескольких, да/нет, смайл-рейтинг, NPS, шкала, короткий/длинный текст), настраивает обязательность по каждому, включает «Анонимный опрос», публикует — получает ссылку вида `/s/<slug>`.
- **Респондент**: НЕ обязан быть в Vibe. Ссылку можно отправить кому угодно — страница рендерится отдельно от платформы (без сайдбара/топбара/логотипа/цветов VBI), нейтральный стиль, своя страница «Спасибо» после отправки и «Опрос недоступен» для неактивной/несуществующей ссылки.
- **Анонимность — на уровне данных, не UI.** Если включён «Анонимный опрос», в ответе не сохраняется вообще никаких данных об отвечающем (ни id, ни имени) — даже если у респондента в браузере была действующая Vibe-сессия на момент отправки. Для неанонимных опросов id/имя сохраняются, только если такая сессия реально была (анонимный с улицы респондент и в неанонимном опросе не привязывается — писать «аноним» нечем).
- **Статусы опроса**: `draft` (не виден публично) → `published` (ссылка активна, принимает ответы) → `closed` (снят с публикации кнопкой «Остановить» — ссылка перестаёт принимать ответы и отдаёт «недоступен», старые ответы и результаты сохраняются). Редактировать вопросы можно в любом статусе; при повторной публикации `closed`-опрос снова становится `published` по той же ссылке (slug не меняется, если не менялось название).
- **Результаты**: воронка «начали / завершили / конверсия» (завершил = ответил на все обязательные вопросы), по каждому вопросу — распределение ответов (кол-во + %) для вопросов с вариантами/рейтингом, для открытого текста — список сырых ответов без какого-либо ИИ-анализа (это Phase 2+).
- **Явно вне Phase 1** (может появиться позже, продукт-овнер не утверждал): галерея шаблонов опросов, собственный домен/QR-код/кнопки шеринга в соцсети под публичной ссылкой, автоматический анализ открытых текстовых ответов нейросетью, продвинутые настройки (SSO для респондентов, капча, ограничение по IP, промокоды за прохождение, ветвление вопросов по предыдущим ответам, история версий опроса).

## 11. Как поддерживать этот документ

При изменении **бизнес-правила** (формула дней, этапы, что входит в баланс, лимиты, матчинг оргпанели, удаление сотрудника, поиск в базе знаний, правила кота оценки) — обновить соответствующий раздел здесь **в том же коммите**, что и код.  
`CHANGELOG` — кратко «что поменяли»; `PRODUCT` — актуальная правда «как сейчас устроено».
